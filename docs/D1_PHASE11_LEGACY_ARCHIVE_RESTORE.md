## 1. 既存GASとの対応（変更しない既存仕様）

### 旧7列試合版の読み取り

現行`matchLoad_`はシートの`試合版管理`9列読み取り値について、`Number(versions[0][8]) || 1`、`Number(row[7]) || 1`として旧7列単一行を読める。*旧原本の物理列数を実Sheetsの返却値だけで断定できない*。新しい`0002_business_skeleton.sql`の`match_revision_chunks`は`chunk_index`と`chunk_total`が必須で、旧7列相当行をそのまま挿入することはできない。

第11工程では、原本の7列配列または9列の後ろ2列が空白/Nullの**旧形式とみなせる候補**を、メモリ上のみ`chunkIndex=1,chunkTotal=1`へ投影する。しかし、元7列と9列の空欄の違いは原本にそのまま保管し、9列化を原本上書き／自動移行とみなさない。後ろ2列が片方だけ空、明示ゼロ、重複、範囲外のときは移行前ゲートで拒否する。**GASの寛容な`|| 1`動作を新D1へ無断一般化しない。**

原本の行番号・書式・日時などは別のネイティブGoogle Sheet保全が必須。今回のコードは7/9の**セル値配列**と候補を分離するだけで、物理シートの完全復元を実装したわけではない。

### 試合削除アーカイブの復元可能性

現行`matchDeletePlan_`は削除対象の日程に対し、次の**物理行番号と行配列**をJSONに格納する。

| JSONフィールド | 旧Sheet/列数 | 元情報 |
|---|---|---|
| `targets["試合セッション"]` | 5列 | 日程ID、現役revisionId、session/settings版数、日時 |
| `targets["試合版管理"]` | 9列 | 該当日程の**全試合版（旧7列は末尾2列空欄の可能性）**とSHA/分割/生成履歴 |
| `targets["試合操作履歴"]` | 7列 | 操作ID・actor・操作と版IDの監査 |
| `links` | 6列（閲覧リンク） | 削除前の未失効閲覧リンクを、行番号ごと保持 |

`schema=1`、practiceId、sessionVersion/settingsVersionもJSON内に存在。アーカイブは**JS UTF-16 12,000 code unitで分割**し、先頭のみ`prepared`で永続化。その後に閲覧リンクを失効し、`試合版管理`→`試合操作履歴`→`試合セッション`を**各表の物理行番号降順**に削除し、先頭アーカイブ行を`completed`へ変更する。監査の追記失敗はcatchされるため、削除完了と通常の操作履歴の存在は同義ではない。

**重要**：`prepared`では途中で削除された可能性があり、復元/再削除を自動実行してはならない。元リンクIDや日時・行順、全試合版、旧actorを捨ててはならない。削除アーカイブ本文には**独立したSHA列がない**ため、JSONの構文、元行番号、内部試合SHAがすべて正しくても閲覧リンク等の「構造的に妥当な値の改変」は検出不能。完成状態と真正性は別の概念として管理する。

## 2. 第11工程のオフライン検証実装

- `d1-staging/phase11/legacy_archive_guard.py`：既存Sheets/D1/ネットワークへのアクセスと書込が不可能なPython純粋関数。`scope="fabricated_offline_only"`のみを受理。旧7/後ろ2列空の7列互換投影と元行配列の保持（`normalize_revision_cells`）、JSON `schema=1`の削除アーカイブ分割/完了状態/元行番号/対象練習日ID/版数/リンク未失効/版SHA/有効版の仮照合（`inspect_archive`）を検証し、仮復元は**メモリに元JSON・元行番号をdeep copyするのみ**（`virtual_reconstruct`）。
- 旧形式でも原本を保持し、9列相当の投影だけをD1候補とする。後ろ2列空の9列が本当に「物理7列原本」かは原本のネイティブコピー/メタデータと照合するまで**未確定**。
- 試合版のUTF-16高/低サロゲートが分割境界に現れる場合、**コード単位のバイト列を連結した後**にUnicode化してSHA-256 UTF-8と比較。 `staging`の古い未完了版を`ready`に勝手に変更しない。有効版自体が未検証、欠損、別日程、版数相違ならBLOCKED。
- 旧削除アーカイブの先頭ステータスが`completed`、全チャンクに欠落/重複なくJSONを復元できたときだけ`CANDIDATE_ONLY`。結果表示は**カテゴリ別の件数とエラーコードだけ**で、元ID・SHA・JSON本文・金額を返さない。構造合格でも`unverified_provenance=true`・`source_backup_required=true`・`write_authorized=false`・`cutover_authorized=false`。
- `tests/check-d1-phase11-legacy-archive.py`：架空の単一7列版／9列空欄互換／新9列多チャンク版／サロゲート分割／削除アーカイブ複数チャンク／閲覧リンク／セッション／監査行・元行番号のメモリ内往復復元。 prepared、欠番/重複、混在、元行・参照・版数・SHA・stage不整合の拒否を確認し、**アーカイブに独立ハッシュがない限り構造的に正しい値改変を検出できない**ことも架空fixtureで明示する。
- D1 20テーブル・既存47 API GAS_ONLY・第1～10工程・旧会計確定順序/出欠/退会/試合回帰を維持。今回の仮復元はGoogle Driveバックアップ/実D1のINSERT、シート復元用スクリプトではない。

| 判定段階 | 実施方法と確認点 | 未承認時の扱い |
|---|---|---|
| 対象/保全責任 | 移行対象は検証用架空データか本番かを選ぶ。個人情報/LINE ID/領収書本体と履歴の取扱、専用バックアップフォルダの責任者、アクセス/保有期間、コピー失効後の消去と復旧目標を明示承認 | 原本をコピーしない |
| 処理中と整合時点 | 既存GASのロック・試合`staging`/削除`prepared`・会計確定順序/操作IDの残留を確認。最終的な書込停止方法を別途設計して承認。個別Sheets API読取を「同一時刻の原子性あるバックアップ」と呼ばない | 書込停止・設定変更をしない |

### 実際の復旧時の重複回避（将来の承認後）

元行番号の列挙だけで`deleteRow`や`appendRow`を行うのは危険。Sheetはアーカイブ作成後に変わっている可能性があり、物理行番号は他行の増減で移動する。将来の復元器は、隔離済みコピーに対して現役ID・操作ID・revisionId・トークン・承認された時点の整合版数を検査し、競合時は**全体を失敗扱いとして手動調査**。削除前のプライバシー情報を復元して公開閲覧リンクの失効を取り消す操作は、原則として自動では行わない。論理的なロールバックと過去記録の安全な再現を区別する。

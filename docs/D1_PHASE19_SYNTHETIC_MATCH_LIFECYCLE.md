## 今回のユーザー承認とその境界

- **第18工程はA**：SHA不一致の既存46版（現役8+過去38）を**絶対に改変せず**、新規生成の正常な架空試合版だけでD1保存・読込・削除/アーカイブ・復元を技術検証する。旧SHAの値を書き直さず、検証スキップや架空データでの代用によって実旧版の検証完了とも言わない。
- 現行47業務APIのルートは**GAS_ONLY**を維持。GAS、LINE/LIFF、元Sheet、非共有バックアップ、本番、Cloudflare既存公開Worker/既存Read-only Worker/元検証D1（全20業務表0行）、第14工程の架空業務表・会員・金額・実IDには書込みしない。
- **書込先は以前から存在する独立した架空D1** `zenryoku-smash-d1-atomic-fixture-stage`に新たに作る、接頭辞`z_native_fixture_match19_` のテスト表4件だけ。既存の専用Worker `zenryoku-smash-d1-atomic-fixture-worker-stage`に専用gate `NATIVE_SYNTHETIC_MATCH19_ENABLED=true`と一時Bearerを利用。追加D1/Worker/Secretsは作成しない。
- リクエストには生成済みテストID・操作UUID・ブール値以外を受け取らず、状態JSONと操作者文字列はWorker内で**固定の架空値**を生成する。既存シートの本文/IDや外部利用者のデータを持ち込む経路を持たない。回答はSHA確認フラグと匿名件数だけで、JSON/ハッシュ/IDをCIの公開ログに出さない。

## 試合モデルと旧仕様との比較

| 今回の架空モデル | 現行GAS仕様との関係 |
|---|---|
| UTF-8 `crypto.subtle.digest('SHA-256')`、JSON本文は固定架空値。UTF-16 **30,000 code unit**を基準とし、ちょうど境界に生成した架空🏸のサロゲートペアを**分断せず**2チャンクに保存。読み戻し時はindex/total/ready/全体SHA/JSON構造を検証 | GASは `JSON.stringify`→`matchHash_`→UTF-16 `String.slice(30000)`、stage→読戻し→readyを経てポインタ更新。**旧データそのもののバイト同値・GAS分割と完全等価という意味ではない** |
| `D1Database.batch()`に版チャンク、ポインタ、監査を同時投入。監査故障・古い版数では全体取り消し。旧確定B/B①操作ID別対象禁止②監査失敗全体ロールバックを保持 | 実運用のLINE本人識別、役割/日付・試合進行・過去全版/SHA46/個人情報の検査は範囲外 |
| 削除前に原文・SHAを検算。架空アーカイブsnapshot+SHAと削除済みフラグを、操作ID・監査と原子的に記録。**版本文は削除せず保持**。元の有効版参照を外す | GASは削除前の物理行番号・全版行・操作履歴・未失効閲覧リンクをアーカイブして、試合版管理・操作履歴・セッションを**物理削除**、リンク失効。今回のトゥームストーンは**技術候補であり、旧業務仕様と完全同値ではない** |
| アーカイブ検証プレビューは元の状態を再活性化せずSHA検算のみ。架空限定の復元候補は同じ原文版を再参照し、監査と一括コミット、失敗時は削除済みのまま | 現行GASにはこの自動復元業務APIはない。実アプリの「復元ボタン」「権限」「アーカイブ保持」への採用には**追加ユーザー判断が必要** |

## 次にユーザー判断が必要な仕様差（本業務APIへ採用する前）

**論点：D1試合削除・復元を旧GAS互換の「物理削除＋完全アーカイブ＋管理者による手動復旧」方式にするか、D1候補の「論理削除＋アーカイブ保全＋新規認可付き復元」方式にするか。**

- **案1（旧仕様優先・既定）**：旧GASどおり、対象の全版/履歴/未失効リンク/物理行順等を保全してから削除し、明示承認を受けた復旧フローでしか再有効化しない。移行後も権限/履歴/リンク失効の再現が重要。
- **案2（安全性/運用改善候補）**：データの正本は保持し、削除は非表示・リンク失効/参照不可化、履歴監査と原子的にコミット。権限と操作IDで再有効化する新しい管理者用復元機能を追加。ただし旧アプリと異なる仕様になるため**ユーザーの別途明示承認なしに業務APIに採用しない**。削除済みデータの保存期間/個人情報の削除要求/他機能での露出防止を設計する必要あり。

**両案とも未解決**：SHA不一致旧46版の原文真正性、旧日程削除/閲覧リンク/操作履歴等の完全ロスレス再現、財務/権限/本人/退会、実データ移送と同意、保持/廃棄・復旧責任、本番切替。性能改善・LINE連携開発はD1移行完了まで保留。本番反映は従前どおり個別の事前承認が必須。

## 2. 新たに確認した移行禁止要因：試合版ハッシュ

`試合版管理`の現存8行/8版を、再分割なしの連結本文に対してSHA-256（UTF-8）で**読み取り専用**再計算したところ、保存されている64文字のハッシュと**8行すべて不一致**。8行はいずれも`ready`、JSONとして構文は正常、チャンク数/並び/IDは構造正常。SHA計算は英文単数ブロック・複数ブロック・日本語・絵文字の独立既知ベクトルで照合し、Google SheetsのuserEntered/effectiveおよび値取得APIでも本文一致を確認。

`試合セッション`の有効版参照は存在し、`ready`だが、その版も上記8件の一部である。現行GAS `matchLoad_`はロード時にSHAを照合するため、**実GASへの読込試験を実施していない現段階でも、D1移行前の要調査・no-go**。原因は現時点で未確定（架空データ作成時のハッシュ代入、後日編集、文字列・文字コード変換等のいずれかを断定しない）。**原文JSON・元ハッシュを公開GitHubに載せない／データ修正・ハッシュ再生成を無断実施しない**。

`日程削除アーカイブ`3行/3グループ、`試合削除アーカイブ`34行/5グループ、`参加者操作アーカイブ`1行、`ビジター審査アーカイブ`2行について、分割総数・連番、先頭`completed`、JSONパース、`schema=1`などの限定構造検査にエラーなし。前回の一時的「削除アーカイブJSON内部形式が1件異なる」検出は、**空白ステータスセルの未定義表現を異常扱いした検査側の誤判定**と判明。該当の実JSONは正常に読めている。ただし旧削除アーカイブはSHA列がなく、改変されても妥当なJSONが成立する場合を自動検知できない。

**監査の限界**：複数のAPI呼出しに跨る観測は原子的な同時スナップショットではない。Sheets APIの`userEnteredValue/effectiveValue`とGAS`getValues()`のネイティブDate等の差、非業務ガイドの全書式、条件付き書式・保護設定、行/列プロパティ、領収書Drive添付の実体、共有権限や本番ワークブックは網羅していない。「業務20タブ内の既存グリッド値」と「正式な完全バックアップ」は異なる。

## 3. 次回以降のバックアップ・復元手順案（**未実行**）

**第Aゲート：移送対象・権限・保持期間の承認。** 利用者に本番/検証の対象、個人情報・領収書の移送先/アクセス制御/保有期間/削除とバックアップを明示し、実データコピー前の承認を受ける。現在のD1用トークンをGoogleの広範囲権限や本番権限に置き換えない。

**第Bゲート：単一整合時点の確保。** 原本への新規書込を止めるための安全な管理者メンテナンス状態、操作ID完了/未完了/準備中アーカイブを照合し、**ソースの取込前後で版数・件数・監査末尾が変わらない**ことを検証。ユーザーに確認するまで現行GAS/Worker/UIへロック機能を追加しない。既存業務を止めずにシートだけ別時点で読取る方式を正式移行用の原子的バックアップと呼ばない。

**第Cゲート：原本ネイティブコピーの保全。** 承認後、Google DriveのネイティブGoogle Sheetsコピーを限定アクセスの専用領域に作成し、**ガイド含む全21タブ、数式、非表示、書式、検証、関連保護/共有設定を必要に応じて個別照合**する。コピーが元の共有権限・Apps Script・保護をすべて自動継承したとは仮定せず、それぞれ照合する。原本は不変更。独立した保存期間/復旧責任者/削除ルールを明記。

**第Dゲート：読取専用セル・行順の署名付き検査。** 元/コピーのフル列・物理行番号・型・表示形式・数式・JSON/操作履歴・試合SHA・収支の行順と確定状態を照合。PII/JSON/金額本文や原ハッシュをGitHub/Actionsへ書かない。SHA-256は単なる完全性チェックであり、改変できる人がdigestも変更できるなら本人性/改変防止の証明にならないため、保管権限と不可変化/監査も必要。

**第Eゲート：隔離復旧演習。** 原本とは別のテスト用Google Sheet/将来の検証用D1に復元し、ガイド・隠しシート・日時/曜日・収支残高/確定順序・退会監査・試合版/アーカイブ・領収書・権限と再送を検証。原本の公開URL/既存LIFF/設定済みIDを変えない。失敗時はデータを捨てず、復旧手順を再設計。

**第Fゲート：検証用D1への承認付きデータコピーとread shadow。** 第A～Eを全て通過して初めて実業務データ転送の可否を利用者に報告。既存47 APIの`GAS_ONLY`維持、既存WorkerへのService Bindingや正本切替は別PR・別承認。無承認二重書込/カットオーバー禁止。成功後も本番反映は明示承認。

## 4. 今回のコードと試験の意味

- `d1-staging/phase9/snapshot_guard.py`：**架空データ専用**の21タブ／20業務列契約の型付きスナップショット、ハッシュ、復元メモリコピーを検証する純粋関数。表の原稿をDriveにコピー/Cloudflareへ投入する機能は意図的に実装しない。元セル入力型、数式、フォーマット、行番号と空行、非表示タブ、シートID、JSTを維持する。
- `tests/check-d1-phase9-snapshot.py`：架空セルの数値/文字列/boolean/数式、日時書式、空行、隠しタブ、ヘッダー、チェックサム、元データ改変、無断実データ利用をfail-closedで確認。
- `d1-staging/phase9/readiness_gate.py` と `tests/check-d1-phase9-readiness.py`：**試合SHA不一致が1件以上／prepared残存／未検証バックアップ・復旧・本人承認が1件でもある場合はBLOCKED**。全条件真の架空ケースでも`CANDIDATE_ONLY`で、操作権限/データ書込/切替を付与しない。
- CIは既存の第1～8工程、47 API GAS_ONLY、旧会計・出欠・退会・試合回帰を維持。

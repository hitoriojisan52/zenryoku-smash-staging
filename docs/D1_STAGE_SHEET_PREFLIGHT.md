## 1. 実施方法／監査の限定

- Google Sheetsメタデータで全21タブ（検証ガイド1＋業務20）、locale `ja_JP`、timeZone `Asia/Tokyo` を確認。
- 業務20タブの**定義済み先頭列**（最大A:P）をそれぞれ実際のグリッド末尾まで `UNFORMATTED_VALUE` で1回ずつ閲覧し、ヘッダーを除く「1つ以上値のある行数」と、設計されたキーの欠落・重複を計数した。**値・氏名・LINE ID・レシート・金銭明細・試合JSONはログ/PRへ出力しない**。
- 検証の対象は指定した列範囲内の現存セルに限る。余分な列、表示形式以外のフィールド、条件付き書式、全数式、手入力とGAS書込の区別までの包括的監査ではない。
- 主キー重複と一部参照整合のみを照合。すべての業務契約・操作履歴・日付型がD1へ安全に移行できると結論しない。
- GitHub ActionsでこのGoogle Sheetsを自動参照するSecret/OAuthは追加せず、**D1 Remoteへ行データを一切書き込まない**。既存D1 20テーブルの構造とビジネス書込先は変更しない。

## 3. 移行阻害要因（原本を変更しない）

### BLOCK-1：チーム所属の複合キー重複と履歴

`チーム所属`5行に対し、同じ`(teamId,memberId)`の組み合わせが**1組・3行**存在（有効1行・無効2行）。そのほかの2行は別のキー。

現行GASの`member_`は、該当会員の`active=true`かつ有効な当番チームへの所属が**1行でも存在する**場合に`duty`と判定する。無効2行を単純に捨てれば現役ロールだけは同じになる可能性があるが、**シート上の過去行情報を失い、データのロスレス移行条件を満たさない**。

現在のD1候補スキーマ`team_memberships`は`PRIMARY KEY(team_id, member_id)`であり、3行の直接投入は失敗する。以下の解決案を別途判断するまで**チーム所属の取り込みは禁止**。

- **推奨候補A（履歴保持）**：全原本行を別履歴テーブル（行IDや元の行順を保持）で保持し、現役ロールの計算は旧GASの`any(active && enabledTeam)`に一致する別ビュー/ロジックへ移す。D1スキーマの追加を含むため、ユーザーの仕様判断・履歴保持方針の承認が必要。
- **候補B（現役だけに集約）**：現役判定は維持できる可能性があるが、無効2行を失う可能性があり、現時点で**採用しない**。
- **候補C（移行保留）**：所属・権限を当面GAS/Sheets正本に残す。承認前はこれが現在の動作。

### BLOCK-2：日付セルの物理型が混在

`UNFORMATTED_VALUE` の日付列では、`練習日程` **数値4件＋文字列1件**、`全体収支管理表` **数値7件＋文字列2件**、`操作履歴`の日時 **数値210件**を確認。`get_spreadsheet_cells`で小さく範囲を限定した確認では、それぞれ日付・日時型の書式を持つ数値セルがあった。日付列3箇所の部分確認で`formulaValue`は0件（**全タブ／全数式ゼロの証明ではない**）。

D1の`practice_date`、`ledger_date`、`timestamp_raw`はTEXT設計。Google日付シリアル値と文字列をJST基準で可逆に正規化する方法、`HH:mm`の時刻と生ログ日時の保持方法を確定し、日付境界と繰越/報告時刻のfixtureを合格させるまで**実データ変換は禁止**。

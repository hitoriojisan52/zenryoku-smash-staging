# D1第5工程：「チーム所属」同一会員3行の発生原因の再調査（2026/11/21）

この文書は過去の確定仕様・GitHubの実装・接続検証用スプレッドシートの**読み取り専用**監査の結果。原本の行・履歴・D1の構造やデータ・GAS/Worker/LIFF/本番を変更しない。

## 結論（確認済み）

11月21日の20タブ監査で発見した同一 `(teamId,memberId)` の3行（`active=FALSE` 2行、`TRUE` 1行）は**退会者の行ではなく、11月20日に追加された検証専用自己権限切換 `stage.selfRole` の結果**。現在の`メンバー`に対象IDが存在し、同一IDは`退会履歴`には存在せず、退会履歴にあるIDを参照した`チーム所属`行も0件。GitHubの旧コード・引き継ぎ・スプレッドシートの操作履歴に整合。

### 検証用操作履歴で確認した時系列

同じmemberIdに対する`stage.selfRole`の成功結果が6件あり、順に以下を記録する（氏名・会員ID・LINE ID・生のログはGitHubに出さない）。

| 順 | 操作後のロール | `チーム所属` の挙動（実コード） |
| --- | --- | --- |
| 1 | duty | 当該teamId/memberIdのactive行がないため`TRUE`行をappend |
| 2 | member | 既存の`TRUE`を`FALSE`に設定（行は残す） |
| 3 | duty | active行がないため新しい`TRUE`行をappend |
| 4 | member | 直前の`TRUE`を`FALSE`に設定 |
| 5 | duty | active行がないため3つ目の`TRUE`行をappend |
| 6 | admin | `メンバー.isAdmin=true`だけを更新し、チーム所属の`TRUE`行は維持 |

現在のシート3行＝`FALSE/FALSE/TRUE`はこの6操作の結果と**一致**。ただし個々の行の作成時刻は`チーム所属`単体には記録されておらず、監査根拠は別の`操作履歴`に存在する。

## 過去の実装・確定仕様との照合

1. [v0.16.1の権限仕様](roles-and-rich-menu-v161.md)：`admin`／`duty`／`member`の3ロール、当番担当は開催日を問わず共同操作。権限は必ずサーバー側で判定。
2. [v0.16.53の退会・再入会](stage-v1653-withdraw-rejoin.md)：退会時、該当`メンバー`・`チーム所属`・`登録申請`を**物理削除**し、退会履歴と旧会計/出欠/試合/監査を保持。再入会で新memberId・一般メンバー・当番所属なし。このルールでは退会した同一memberIdのチーム所属行は残らない。
3. [v0.16.57の権限変更の実機受入](SESSION_HANDOFF.md)：`member.manage.role`で当番担当→一般メンバーを実行し、`チーム所属.active=FALSE`で行を残した実測が記録されている。
4. [v0.16.80検証専用自己権限切換](stage-v1680-self-role-staging-message-semantics.md) は[PR #94](https://github.com/hitoriojisan52/zenryoku-smash-staging/pull/94)で追加され、本番環境への移植を**禁止**する別テスト機能。GAS実コード`accessStageSelfRoleV1680_`は`member`でactiveな所属をFALSE、`duty`でactive行がなければappend、`admin`で所属には触れず`isAdmin`をTRUEにする。
5. GAS `member_`は**activeな会員＋isAdminならadminを最優先**、それ以外は有効チームに所属するTRUE行が1つあればduty、なければmember。`admin`とTRUE行が併存しても最終権限はadminであり、現行GAS上の矛盾ではない。
6. 現行D1候補`team_memberships`の複合PK `(team_id,member_id)`は、「現時点の所属状態を1行で持つ」と読むなら整合的。**元シートの繰返しのFALSE/TRUE行をイベント履歴テーブルとしてそのまま利用することが確定済みの業務仕様だったわけではない**。正しい変更操作の監査は既存の`操作履歴`に記録されている。

## 先の提案の訂正と今後の設計候補（未適用）

旧[D1_STAGE_SHEET_PREFLIGHT.md](D1_STAGE_SHEET_PREFLIGHT.md)で「3行を消すと履歴が失われるため別履歴テーブル必須」と読める説明をしたが、**役割変更の監査履歴と、3列しかないチーム所属の残存行を同一視したのは不正確**。退会によるものか利用者に問うべきではなく、開発側で原因を調べるべきだった。

**暫定設計候補**：D1 `team_memberships`は現在の**有効な所属状態（同一キーにTRUEが1行でもあればactive）を1行**に集約し、ロール判定は旧GASと同一（`isAdmin`優先、次に有効チームのactive所属、その他member）とする。降格はTRUE→FALSEへのUPDATE、昇格は重複INSERTではなく同一キーの有効化、**操作の前後・日時・操作者・操作IDは`操作履歴`の既存監査契約を保持**。現在の3原本行については移行の監査用スナップショット/バックアップで原型を保持し、行の自動削除や原本上の集約はしない。

この方式ならD1複合PK自体を緩和する必要はない可能性が高い。ただし、監査の長期保存・退会時の過去ID扱い・原本スナップショットの保存方法・同期/復旧は未設計であり、**今ここで実レコードの集約やD1投入を実施する承認にはならない**。GASの実行時の状態解決を静的集計へ置換する前に、架空fixtureで`admin→duty→member→duty→member→duty→admin`、チーム無効化、退会/再入会を含む再現試験が必要。

## 移行前に保持するガード

- 検証用・本番用のスプレッドシートを変更しない。本人ID、LINE ID、金額、元の操作ログを公開リポジトリへ保存しない。
- 現時点ではD1の`team_memberships`や監査履歴・バックアップを作り直さず、47の既存APIは`GAS_ONLY`のまま。
- 新方式はD1移行上の**設計案**であり、本番に影響する移行は既存仕様の同値検証・バックアップ・ユーザー事前承認後に判断。

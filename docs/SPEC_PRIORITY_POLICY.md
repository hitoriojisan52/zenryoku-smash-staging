# 全力☆スマッシュ — 仕様優先順位と変更影響レビューの正式ルール

制定日：2026/11/19。参照元：ユーザーが2026/11/19に明示した優先順位。検証用GitHubの変更判断に適用。旧仕様の具体的な内容は、旧アプリ実装と記録／資料により別途確認する。

## 仕様の優先順位（ユーザー指定の順序を厳守）

1. **既存アプリの確定済み業務仕様・動作**
2. **既存機能との整合性と安全性**
3. **これまでに協議した実装ルール**
4. **新しい画面・機能の実装方法**
5. **明示的な変更指示の仕様**

5について、1～4への**優先順位上の影響・機能差異・安全上の懸念**が判明した場合は、実装によって暗黙に上書きせず、**ユーザーに報告する**。変更指示そのものを無視するという意味ではない。問題がなく両立できる範囲は進め、両立しない箇所は「何が変わるか／影響する画面・データ・権限／選択肢／推奨する対応」を明確にし、ユーザーの追加判断を得てから変更する。

## 開発中の必須チェックポイント

1. **基準の確認** — 関連する既存アプリの画面・ソース・業務仕様、ユーザーが承認した実装ルール、直近のGitHubソース／テストを確認する。旧資料にアクセスできなければ未確認と明記し、推測で正本を作らない。
2. **変更影響の仕分け** — 以下を必ず分離する。
   - 「維持する仕様」：現行の業務ルール、ボタン活性条件、処理順序、レイアウト、権限、金銭計算、既存データ、異常系
   - 「依頼された変更」：ユーザーが具体的に求めた範囲
   - 「衝突／懸念」：新しい指示が1～4のいずれに影響するか、検証・移行上のリスク
3. **懸念の報告** — 衝突がある場合、対象仕様の優先順位番号、旧動作、新指示で変わる箇所、安全性とデータへの影響、複数の解決案を示す。**懸念のある不可逆操作・仕様変更は了承前に本番にも検証用実データにも適用しない**。明確に分離できる非破壊作業は継続可能。
4. **実装と回帰試験** — 許容された差分だけを変更し、既存の業務制約をテストに固定する。画面だけでなくAPI／サーバー側でも検証する。変更なしの機能にまでデグレードが出ないことを確認する。
5. **反映と引き継ぎ** — 検証用ブランチ、PR、CI、検証環境デプロイ、ユーザーの実機確認を区別して記録する。本番反映は従来どおり事前承認制。問題がなければ本ドキュメントに変更を加えず、機能別の設計・テストを更新する。

## 報告形式

| 項目 | 書く内容 |
| --- | --- |
| 変更依頼 | 対象画面／操作と期待される新動作 |
| 関係する優先順位 | 1～4のどの既存仕様に影響するか |
| 既存仕様 | どのバージョン／資料／実コードで確認したか |
| 影響・懸念 | 保存済みデータ、収支、権限、画面、運用、復旧への影響 |
| 安全に進められる範囲 | 衝突しないUI・テスト・調査・文書化 |
| 判断が必要な点 | 旧仕様維持／変更承認／代替案の選択 |

## 現時点で特に保護する既存仕様

- 全体収支管理表：**先行する未確定行があれば後続の確定を非活性にし、GASでも確定順序違反を拒否**。月またぎ・同一日を含む。v15の操作ボタン表示・配置も維持。
- 集金・収支・出欠・ビジター・試合進行の連携と確定済み金額の保護。保存処理は本人認証、権限、操作ID、排他ロック、二重送信対策を維持。
- 管理者が一人しかいないときの権限変更禁止。メンバー退会はUIがあるだけでは有効化しない。過去の出欠・集金・試合、再入会、LINEユーザーIDの整合性を保護する。
- UIの処理中は「初回・手動更新・保存時のみ全画面ロック／自動更新は非ブロック」。画面右上の閉じるは管理画面レベルのみにし、確認・修正ポップアップには新設しない。
- 旧資料と後日の指示で食い違いが生じる場合、**後日の指示を無条件で優先しない**。まず上記優先順位による影響を報告する。

## 2026/11/19に承認された具体的な整合性判断

**優先順位の並び自体は変更しない。** 事前に報告した相違点について、ユーザーから次の選択が明示された。将来月・未来日収支は未確定のまま表示可（A）、その他の収支区分を保持（B）、全体収支管理表の確定済みは役割別1ボタン表示（C、ほかの画面へ一般化しない）、利用申請に氏名カナを追加し参加者の区分内カナ順を共通適用（D、旧データは推測して上書きしない）、引継ぎの新旧記述を整理（E）。詳細は[stage-v1657-registration-kana.md](stage-v1657-registration-kana.md)参照。**残高計算・旧収支確定順序・サーバー権限・過去履歴は引き続き優先順位1～2として保護。**

## 2026/11/21 — D1移行先だけに適用する承認済み仕様変更（①B・②B）

第16工程のユーザー判断により、[確定仕様：D1の対象ID厳格化・試合監査原子化](D1_APPROVED_OPERATION_MATCH_ATOMIC_POLICY.md)を正式採用。

1. 同じ操作IDを**別の対象へ再利用した場合は拒否（B）**。既存の操作種別・操作者一致に加え、D1移行先では対象ID一致も必要。同一操作の再送は結果を再現し、二重反映しない。
2. 試合版の有効ポインタ変更後に**操作履歴記録が失敗した場合は、版・ポインタ・履歴をすべてロールバック（B）**。保存だけ成功した扱いにしない。

この2点は旧GASの挙動との差異を説明したうえでの**明示的な承認例外**である。**元GASを今すぐ変更するという意味ではない**。旧GAS/Sheetsが正本の期間は現行動作を維持し、D1業務API完成・本人認証/会計/試合保存・復旧/実データの同値性と安全性確認後、別途承認される切替地点で新D1仕様を採用する。未承認の仕様差・SHA不一致・本番反映は従来どおりNo-Go。性能改善・LINE機能拡張はD1移行完了まで保留。

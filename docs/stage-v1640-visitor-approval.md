# v0.16.40｜ビジター申請・承認／却下ワークフロー（検証環境）

## 確定仕様（2026-11-18）
- **申請者**：有効な登録済みLINEメンバー全員（一般／当番／管理者）が、自身のIDでビジターの名前・カナ・開催日・備考を入力。申請内容は「ビジター申請」へ保存され、承認前は「出欠回答」「集金」「試合人数」に含めない。
- **申請状況**：登録者本人だけが自身の申請（承認待ち／承認済み／却下済み）を確認できる。照会は毎回GASのサーバー側memberIdで絞り込み、クライアントから申請者IDを指定させない。
- **審査者**：管理者のみ全申請と依頼者を閲覧し、「承認／却下」可能。両操作には必須の確認ポップアップを表示。
- **状態遷移**：`pending -> approved`（参加者一覧に追加）、`pending -> rejected`（未追加）、`approved -> rejected`（参加者一覧から除外）。`approved`の「承認」は非活性、「却下」は有効。`rejected`は両方非活性・再承認不可。
- **支払済みビジターの却下**：対象開催日の**収支未確定**なら認める。集金チェックと参加者の回答を削除し、収支額と残高を再計算する。**返金概念、返金ボタン、現金の入出金処理は実装しない**。収支確定後はサーバー側で承認・却下・削除を拒否する。後続の確定残高を変えるケースも従来どおり拒否。
- **試合実績との整合**：対戦表作成済みなら承認および承認済みの却下を拒否し、対戦表削除を案内する。承認待ちの却下も収支確定後は不可。
- **直接削除**：承認済ビジターの「参加者一覧 → 削除」は**管理者なら可能**。内部的に同一IDの「却下」処理へ委譲して、申請状態も必ず`rejected`に変更する。集金チェック済みでも収支未確定なら消せる。**当番担当は承認済ビジターの削除不可**（承認・却下権限は管理者のみ）。旧方式の既存ビジター行は従来どおり。

## 実装
- 検証用Sheetに「ビジター申請」（申請ID、開催ID、固定参加者ID、氏名、カナ、備考、申請者memberId、状態、版番号、申請日時、審査日時、審査者、審査操作ID）と非表示の「ビジター審査アーカイブ」をヘッダーだけ新設。
- API：`/api/visitor/request`（一般メンバー以上）、`/api/visitor/mine`（本人の申請のみ）、`/api/visitor/admin-list`（管理者のみ）、`/api/visitor/decide`（管理者のみ）。旧`/api/visitor/register`も承認待ちにする互換別名であり、無承認の直接参加者登録は不可。
- GASはシート操作前に`ScriptLock`、`operationId`監査、`expectedVersion`、申請状態の再確認。審査時は元データ・財務対象を復旧用にアーカイブ＆フラッシュ後に更新。途中失敗した操作のアーカイブが`prepared`のままなら該当申請の審査を停止し、管理者に復旧を促す。二重実行は同操作IDを認識。
- 管理者の「⚙ 運用管理」に「👤 ビジター管理」、一般メンバーのビジター申請画面に「申請状況を更新」と申請一覧を設置。本人以外の申請は画面/APIどちらも不可。
- 登録済み一般メンバー向けの専用画面は既存`live.html` LIFFの`?visitor=1`モードで利用可能（既存のLINEトークン自動認証を使用）。当番・管理者でも同モードなら集金・財務画面を表示しない。
- 旧「LINE参加連絡・予定修正」リッチメニューAは**別のGAS Webアプリの`LineLiff.html`**。そのソースは本ステージングGitHubリポジトリに存在しないため、このリリースでは**元画面に新ボタンを付ける変更をしていない**。元のデプロイURL・LIFF ID・設定を勝手に変えない。A画面からのリンク導線を直接設置する工程は別途必要。
- 本番未変更。検証用データの申請／却下／集金は一切自動で作成せず、CIではインメモリデータを使用する。

## 検証ポイント
1. 一般メンバーで申請。申請者画面では承認待ち、運用管理の参加者一覧には出ない。
2. 管理者でビジター管理から承認。確認ダイアログ後、承認済みになり参加者一覧へ。
3. 承認済みでは承認非活性・却下は有効。却下の確認後は参加者一覧から消え、申請は却下済みかつ両ボタン非活性。
4. 収支未確定の集金チェックがあるビジターを却下して集金記録・残高が取り消される。
5. 収支確定済みで却下が拒否されること（対戦表がある場合も拒否）。メンバーが他人の申請を閲覧できないこと。

# v0.16.76 — 操作優先・非ブロック読込方針と対戦表反映実行の設計

2026-11-20。ユーザーがv0.16.75の集金画面起動復旧を実機で確認。共通方針は「可能な限りスピナーを出さず、ユーザー操作を優先」「必要なスピナーでは具体的な処理名を表示」。検証環境のみ。本番未変更。

## 今回の第1段階の改修

- 現金確認：先にダイアログを開き、帳簿残金・差額を読み込み中と表示。閉じるは活性。帳簿残金確定まで保存不可。
- 全体収支管理表：前月繰越の仮行のみ先に表示し、他の残高・行は読み込み中。閉じる活性。完了後に旧v15の残高計算・確定順序・権限別操作を描画。
- 練習日程マスタ、参加者一覧、ビジター申請、ビジター管理、メンバー権限管理：ダイアログを先に開き、データ欄を読み込み中と表示。閉じるをブロックしない。
- ビジター申請の「履歴」ボタン削除。申請カード・開催日選択は残す。
- 集金の当日補正・当日支出：保存時は全画面スピナーを使わず、金額欄と競合する集金操作だけ一時停止。GASのScriptLock、版番号、operationId、結果不明時の再照合を維持。
- 「その他の収支」日付：立替精算と同じ曜日表示。開催場所・費目名の入力例「団体戦費用捻出」。
- 今回は初回表示が中心。手動更新や確定・解除・削除・承認など書き込みは既存の全画面ロックを維持し、次段階で個別評価する。

## 対戦表「反映実行」の実現性（未実装）

**実現可能だが、現行APIのまま単に通信を遅らせるのは不可。** 現在のmatch.jsは対戦表作成前のコート・先行生成数・固定グループ・除外参加者をローカル下書きに保持する一方、作成後の参加状態・固定グループ・コート・先行生成数変更は都度/api/match/changeへ送信し、sessionVersion/settingsVersionを検証する。試合開始・次試合・終了・再生成・削除は確定済みラウンドも影響するため厳密な競合制御が必要。

提案：①作成/操作でローカル下書きだけを更新し、未反映表示と操作差分、対象practiceId、基準versionを保持。②対戦表作成ボタン右隣の「反映実行」で一回の認証済みAPIを呼ぶ。③GAS側でScriptLock内の全差分検証・基準版照合・原子的な一括更新。④成功後のみ未反映を解除。409競合時は差分を保持し再取得・再編集を案内、自動上書きや自動再送はしない。

現行の/api/match/changeには複数操作のトランザクションがない。新しいbatch/commit API、試合進行中の競合時UX、監査と回帰テストが必要。**今回のPRでは対戦表の通信経路を変更しない。**

# v0.16.76 — 閲覧優先・画面内読み込み・対戦表反映実行の検討

2026-11-20／全力☆スマッシュ **検証環境限定**。本番デプロイ・運用データ変更はしない。起動不能を修正したv0.16.75の実機確認成功が前提。

## 方針と旧仕様との衝突

- 既定の共通UI仕様は「初回・手動更新・保存時のみ全画面ロック、8秒自動更新は非ブロック」だった（SPEC_PRIORITY_POLICY 1～3）。今回の新しい明示指示では**閲覧画面の初回と更新も画面を先に開き、部分読込中を示す**。読み込みの全画面ロックを緩める点が従来と異なる。
- 安全策：読み込み前に当番・管理者の権限確認、読込の状態に依存する変更ボタンは未データ中に使用不可、Closeは有効、閉じた画面や古い別日程の応答は破棄。書き込みの認証・操作ID・版番号・GAS ScriptLock/確定済みロックを省略しない。
- 保存の結果不明時は自動再送を行わず、最新の状態を照合するまで関係する会計操作を停止する。ビジター承認・退会・収支確定などは従来の全画面ロック/確認を維持。

## 通信・性能と残る課題

- 今回は **体感上の操作待ちを解消するUI改善** が中心。LINE IDトークン検証、Worker→GAS転送、GASのLockService、Google Sheets読込時間を省略・高速化するものではない。
- ビジター申請画面は従来から `Promise.all` で日程と申請情報を並列GETしており、そのまま。ただしGAS側の各GETがScriptLockを使うため実行段階では直列化されうる。
- `readScreen_` は画面ごとに世代番号を保持し、閉じた後・別日程を選んだ後の古い応答を描画しない。通常は同一画面の重複読込を抑止するが、ユーザー操作による収支月切替は新要求を優先する。
- 画面に見える「読み込み中」が長いままなら、GASの構成（同じシートの繰返し取得、ScriptLock競合、Network LINE verify）を別フェーズで計測して対策する。認証・収支データの永続キャッシュや無検証一括書込みには手を付けない。

## 対戦表『反映実行』の実現可能性（今回は実装しない）

### 現状の事実

- 現在の`match.js`では**対戦表作成前**のコート・先行生成数・除外者・固定ペア/トリオの調整は `draftEdit()` によりすでに端末内で完結。対戦表作成ボタンで `POST /api/match/create` が1回発行される。
- 対戦表作成**後**は各種設定、参加者の除外、固定組、試合開始・次試合へ・前に戻る・進行終了・再生成が`/api/match/change`を操作ごとに送り、1回ごとに `SMMatchCore.action`→GASの`matchCommit_`が版管理・ハッシュ読戻し・試合操作履歴へ記録する。
- GASでは `試合版管理` を最大30分割（30,000 UTF-16文字単位）で保存し、ハッシュ照合後に `試合セッション` のリビジョン参照を切り替えている。現行で同時端末操作・結果不明時・undoの保護が存在する。

### 提案：二段階の開発

1. **設定の仮編集＋反映実行**：『対戦表作成』右隣へ『反映実行』を設ける。対戦表未作成時は作成ボタンを**端末内のプレビュー準備**、反映実行で既存`match.create`を1回だけ送信。既存セッションがあるときはコート/先行生成/除外/固定組の変更を編集用ドラフトに溜める。『反映実行』を押すまではサーバー履歴や他端末に反映しない。GASに新しい`match.apply`相当を設け、expectedSessionVersion/expectedSettingsVersionと対象日程を検証し、**1回のScriptLock取得で一括検証→1コミット**する。
2. **試合進行の一括反映は別件として仕様確定**：『試合開始』『次の試合へ』『前に戻る』『進行終了』『再生成』は、実際の全コート同時進行・対戦履歴・undoの意味に関わる。すべて端末内未反映にすると、別端末で実施中試合が遅れて表示され、途中退席時に結果を失う。提案は**進行確定コマンドだけは即時反映を維持**、あるいは進行操作を順番付きの一括トランザクションへ変更し、端末内『未反映』状態を目立つ表示とし、送信前に必ず競合検証する方式。どちらにするかの承認が必要。

### 必須の安全性・技術条件

- 1回の反映で**単一operationId**と対象日程・元版数を送る。GASは本人/管理者権限、最新対戦表版数、最新出欠・集金確定/ロックを再チェック。元版が変わったら409で**ドラフトを自動上書きも自動再送もしない**。
- サーバーの `SMMatchCore.action` 検証を通して初めて確定。必要なら純粋な計算エンジンをブラウザにも提供するか、プレビューは既存表示の参考・未反映であることを明示する。クライアントだけの乱数生成を確定結果と取り違えない。
- 『反映実行』で試合セッション版と操作履歴を一緒に確定し、応答不明時は現在の `match.operation`照会で既存操作IDの反映状況を確認。取り消し・復元・他端末同時操作の回帰テストが必要。
- **意思決定点**：全ボタンの操作を未反映で端末に積むか、設定のみ積んで試合進行操作は即時反映するか。推奨は後者（実試合の進行実態と履歴の整合を保ちやすい）。ユーザー判断まではmatch.js/GAS match系を変更しない。

## 検証

- UI/LINE認証・会計・ビジター・退会の既存回帰と、新しい読込時Close/再オープン/過去応答破棄/当日補正の部分ロック/曜日表示の回帰をCIで実施。
- **CI合格≠実機の性能実測**。LINEからの起動・管理ダイアログの表示順、読み込み中のClose、通信異常時の再試行、実会計変更の版番号は後で検証。ビジター/収支データを勝手に更新しない。

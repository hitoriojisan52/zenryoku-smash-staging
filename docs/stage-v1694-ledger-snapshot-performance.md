## 安全に改修した読み込みの重複

1. `changeMoney_`（`adjustment.set`／`expense.set`）：旧コードは `entries_(ss)` により収支表全16列を1回取得した後、更新候補に値を入れ、`balanceRecalc_(rows,entries_(ss))` の**確認元として2回目の全件取得**をしていた。新コードは**1回だけ全件取得**し、変更前を `original` として保持、変更候補の独立オブジェクト `rows=original.map(Object.assign({},…))` を用いて旧 `balanceRecalc_(rows,original)` を実行する。収支表のデータ取得2→1、残高再計算・確定行残高の変更拒否・会計版本/楽観ロック・集金開始条件・GAS ScriptLock はそのまま。
2. `mutateLedger_`（`ledger.change` の追加・修正・確定・確定解除・削除）：旧コードは `original=entries_(ss),rows=entries_(ss)` で**全16列を2回取得**。新コードは**1回の取得で不変baselineと独立候補を作り、同じ旧時系列順序・確認/解除条件・残高計算と保存関数を実行**する。結果の `ledger` 行と金額/バージョンは変更しない。二重送信排除・操作IDチェックと監査履歴の参照/保存は `dispatch_` で従来どおり **同じScriptLock内**で行う。
3. `sheetRows_`（GASの通常Sheet取得共通関数）：旧コードは `getLastRow()` を**同一呼出し内に2回**実行。新コードは1回取得した `last` を空シート判定と取得範囲の両方に利用する。毎回シートから取得し、ユーザー間・API間・更新間のCacheService/グローバルキャッシュは作らない。ヘッダー定義・必要な列数・欠落シートのSETUP・空シートの空配列を維持する。
4. `deletedPracticeLedgerIds_`（`ledger.list` の削除済み練習日行の判断）：旧コードは全 `操作履歴` A:F を読み、実際には操作種別Bと結果JSON Fしか利用しなかった。新コードはB:F（6→5列）のみ取得し、監査の「delete 成功」「未復元」の厳格な解析、重複検証・壊れたJSONの除外、全履歴の参照を維持する。削除された行の復元可否や一般の収支登録区分の活性条件を変更しない。

### 残高・排他・セキュリティ上の注意

- **GASコード内の処理のみを変更**。変更前・変更後の残高計算、先行する未確定行の確認禁止、月またぎと同日ソート、確定解除を最後の確定行だけ許可する仕様は、**同じ `balanceRecalc_`／`ledgerPriorPending_`／`ledgerLaterConfirmed_`** のまま。
- 変更前スナップショットは同一リクエストの中で新しく取得し、次のリクエストには引き継がない。ScriptLock外からGoogle Sheetsを**手動直接編集する利用者**の変更はロック対象ではないため、運用上の外部直接編集禁止は従来と同じ。
- 集金チェックの `setPayment_`、ビジター承認、本人出欠、現金保存、日程確定、領収書保存、操作履歴の追記、LIFF・Worker、保存APIの15秒タイムアウトと「不確かな結果を自動再送しない」規則は変更しない。
- 既存データに差分を当てたり、11/19～21の確定・解除状態を変更して動作確認することは行わない。**本番環境はユーザー承認があるまで不変更**。

## 検証と期待効果の限界

- 新規 `tests/check-stage-ledger-single-snapshot-v1694.cjs`：**現実のGAS関数**を外部通信のない模擬ワークブックで実行し、当日補正/当日支出の保存、残高再計算、バージョン競合、確定済み残高の変更拒否、収支の確定・解除の順序、バックデート精算禁止、追加/編集/削除の全操作、シート取得getLastRow回数、監査B:Fの削除証跡を検証する。単に静的文字列を検査するだけでなく保存前の値・エラー時の無書込を検証。
- GitHub GAS既存回帰（会計・集金・出欠・現金・ビジター・試合等）と仕様CIを通過後に検証用PRをmainへ統合し、既存検証用GAS Webアプリを**新IDではなく同じデプロイの新バージョン**へ更新する。成功確認の前に反映済みとは言わない。
- **確定可能な改善指標は読み込みの回数削減**：指定2種の金銭変更操作は収支全件読み2→1（50%減）、シート最終行照会は1呼出し2→1（50%減）、収支一覧で削除証跡の転送列は6→5（約17%減）。これらはAPI全体の待ち時間50%短縮を意味しない。Google起動・Cloudflare・LINE認証など外部待ちは残る。
- 実機受入は [検証管理LIFF（性能診断）](https://liff.line.me/2012602642-XBSkXduO?perf=1) で行い、**既存のテスト行だけ**を対象に当日補正・収支編集の通信時間を比較。比較条件（日時・回数・回線・データ量）によるばらつきを明示する。書込みの自動負荷試験や実データ増殖は行わない。

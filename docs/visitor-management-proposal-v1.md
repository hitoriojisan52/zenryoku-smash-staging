# ビジター管理｜要件整理案 v1（検討中、未実装）

2026-11-18。ユーザー提示の業務フローを既存の検証用LINE参加連絡・予定修正、当番管理、参加者一覧、集金・収支、対戦表と整合させるための**提案書**。この文書の作成によって新規ビジター申請データの移行や、既存の即時登録機能の無効化は行わない。

## 1. 画面遷移と権限

```text
登録済みメンバー（一般／当番／管理者）
 LINE公式アカウント →「参加連絡・予定修正」
   → 参加連絡・予定修正の画面
     →「ビジター登録」→ ビジター申請画面（名前・カナ・参加希望日・備考を入力）
        →確認して申請 → 状態「承認待ち」
     →「ビジター登録／申請状況」→ 自分が申請したビジターの状態を確認
     → 承認／却下の結果をビジター本人に連絡（手動）

管理者のみ
 運用管理 →「ビジター管理」
   → 日程・申請者・ビジター情報・申請日・現在の状態を確認
   →「承認」→ 確認ダイアログ → 対象日の参加者一覧へ反映
   →「却下」→ 確認ダイアログ → 参加者一覧から除外
```

LINEの友だち追加だけではメンバー権限を与えない。既存のLINE IDトークン検証と`メンバー`シートの有効な登録を毎回サーバー側で照合する。一般メンバーは**自分が申請したレコードだけ**を閲覧でき、別メンバーの申請や管理者用画面にはアクセスできない。

## 2. 状態遷移とボタン（ユーザー指定部分）

| 現在の状態 | メンバー側の表示 | 管理者「承認」 | 管理者「却下」 | 参加者一覧 |
|---|---|---|---|---|
| 承認待ち `pending` | 「承認待ち」 | **有効**：確認後 `approved` | **有効**：確認後 `rejected` | 非表示 |
| 承認済み `approved` | 「承認済み」 | **非活性** | **有効**：確認後 `rejected` | 表示 |
| 却下済み `rejected` | 「却下済み」 | **非活性** | **非活性** | 非表示 |

**却下は最終状態**。一度`rejected`になった同じ申請の再承認は不可。必要な場合は別申請として新しい`requestId`を発行するかどうかは、運用方針の確認後に決める。

「承認」「却下」の両方で旧運用管理と共通の確認ダイアログを使用する。
- 承認：「○○さんの［日程］参加申請を承認しますか？」「キャンセル／承認する」
- 却下：「○○さんの［日程］参加申請を却下しますか？　承認済みの場合、参加者一覧からも除外します。」「キャンセル／却下する」
- 通信が切れて結果不明の場合は**操作IDを変えての自動再送を禁止**し、「更新」で状態を再取得する。

## 3. データ設計案

既存の`出欠回答`へ即時に書く実装（`visitor.register`）を承認制へ移行するため、将来の検証用シート`ビジター申請`を独立に作成する案。

| フィールド例 | 用途 |
|---|---|
| `requestId` | 申請を一意に識別する固定ID |
| `practiceId` | 対象開催日。表示の日付ではなく固定IDで紐付け |
| `participantId` | 承認時に使用する固定参加者ID。申請時に予約し、一度だけ使用 |
| `name`, `nameKana`, `memo` | 申請されたビジター情報 |
| `requestedByMemberId` | サーバー認証に基づく依頼元メンバーID（画面から指定不可） |
| `status`, `version` | `pending / approved / rejected`＋楽観ロック版番号 |
| `requestedAt`, `reviewedAt`, `reviewedBy` | 申請・承認／却下の日時と責任者 |
| `decisionOperationId` | 冪等性と再送制御のための操作ID |

既存の`出欠回答`は「承認済みの人だけを含む」運用とする。承認待ちや却下済みのビジターは参加人数・対戦表組合せ・集金対象に含まない。承認後に却下される場合は承認時の`participantId`とひも付いた回答を削除／非表示にし、申請履歴自体は残す。名前の一致や行番号だけで削除しない。監査用の操作履歴・復旧用アーカイブは削除しない。

## 4. 既存業務との整合（実装時の重要な制約）

- **承認**：対象日が有効で収支未確定／参加者情報変更可の状態でのみ実行。サーバーロック内で二重承認を防ぎ、一度だけ`出欠回答`に`visitor`区分を追加する。成功後に管理画面・申請者画面を更新。
- **承認後の却下**：参加者回答の除外と集金履歴／帳簿残高の差額を**同一の安全な操作フロー**で処理する。既に集金済みなら、既存`participantChange_`の再計算ロジックを活用する場合でも返金・実現金額の一致を別途検討する（帳簿上の金額だけ取り消して現金を返していない不整合を避ける）。
- **対戦表作成済みの場合**：既存の参加者変更禁止を尊重。却下ボタンは画面上押せても、サーバー側で対戦表を削除してから却下するよう詳細に案内する方式が安全。承認済み本人を試合履歴から黙って消さない。
- **収支確定済みの場合**：既存の確定残高保護を尊重。確定解除と必要な現金調整後でなければ承認済みの参加情報を削除しない。画面は単なる「サーバーエラー」ではなく、必要な事前操作を説明する。
- **開催日を削除する場合**：`ビジター申請`の関係行も日程削除アーカイブ対象とし、申請者画面が消失した開催日を正常に扱えるようにする。
- **新しい4名判定**：承認済みの参加者だけでダブルス成立人数を数える。申請中のビジターを予約人数として数えない。
- **権限**：新しい`visitor.request`・`visitor.mine`は登録済み一般メンバー以上で許可し、`visitor.admin.list`・`visitor.decide`は管理者だけに許可。管理画面のボタン非活性だけでなくGAS APIで状態遷移を強制する。
- **過去の直登録**：現行検証版の`visitor.register`は承認なしで参加者を作るため、本実装時にその導線と権限を見直す。過去の回答を、申請／承認済みという架空の申請履歴へ**勝手に移行しない**。

## 5. 現時点で仕様が未確定の項目（実装前の検討事項）
1. 「ビジター情報」は既存の**日付・氏名・カナ・備考**を基本項目とする案。連絡先の保存は指示があるまで追加しない。
2. 承認済み・**集金済み**を後から却下した場合の現金返金処理（返金済み確認、仕訳、画面の扱い）は運用判断が必要。集金データを単に消すだけでは現金が一致しない。
3. 却下は最終状態だが、同一ビジターが同じ日に再申請することの可否は決める必要がある。表示名だけでは同一人物を安全に判別できないため、申請ID単位で管理する。
4. LINE参加連絡・予定修正画面（旧GAS LIFF）から新画面への導線を設置する際、認証画面のループを避け、**LINEユーザーIDを自動識別**する既存の認証を維持する。参加者情報の登録先は承認後に限る。

**この文書は検討・レビュー用**。ビジター管理の新画面/API/シートは、このリリースではまだ作成・デプロイしない。
